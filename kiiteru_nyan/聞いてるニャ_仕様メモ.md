# 聞いてるニャ v2 — 仕様メモ（叩き台）

この文書は「これに沿って作ってください」の方針書きです。機能の一覧より、**なぜそうなっているか**を先に読んでもらうために書いています。コードは拙い叩き台なので、どんどん直してください。ただし 4章の方針だけは、直す前に相談してください。

## 1. これは何

会話を代わりに聞いておいて、その中の「予定っぽいもの」「手順っぽいもの」を拾い、一覧にして見せるアプリです。本人はそれを見て、要るものだけ選び、違うものは捨てます。

**誰のためか**：聞いたことを覚えておくのが難しい人。つまずく場所は人によって違いますが、だいたいこの3か所のどこかです。

| つまずく場所 | 起きること | このアプリの答え |
|---|---|---|
| 聞き取り | そもそも上手く聞き取れない | 代わりに聞いておく |
| 書き込み | 覚える前に次の話が来て、消える | その場で書き留めておく |
| 引き出し | 覚えていても"見出し"が付いていないので、探せない | 探させない。先に一覧で出す。聞いた日時を見出し代わりに付けておく |

結果として本人は「たぶんこう」で動いて失敗し、怒られます。使う側の言葉でいうと、欲しいのは **「これがあれば怒られない」** です。

### 使われ方の例

**場面A：支援者がそばに居る現場（グループホームなど）**

現場では、いつ・どこに・誰が居るかがだいたい決まっています。だから、そこから外れた話は「要確認」になります。

> 本人「グループホームに〇〇さんがいて、言ってたんです！」
> 支援者「その人B就の人だから、違う人だと思うなぁ…利用者さんか管理人さんかな？聞いてみよう」

（B就＝就労継続支援B型の事業所。日中に通う作業所）
外れた話の中身は、本人が幻覚を見たか、居ないはずの人が実際に居たか、本人が予定外の場所へ行ったか、のどれかで、現場ならほぼ見分けがつきます。

**場面B：記録が無い時（＝今のやり方）**

> 誰に？ → 〇〇さん → （いや居ないだろう…その時間、一緒に居たのは誰だ？） → 確認 → 居たのは別の人／部屋に独り → （幻聴か、聞き違いだな） → 対応

今は本人の記憶から入るしかなく、周りが裏を取りに回っています。記録があれば「この時間に聞いた」から入れます。記録が無ければ、この今までの流れに戻るだけです。

**場面C：付き添いの居ない人**

一人で動いている人は、自分がどこで何をしていたかはだいたい分かります。だから「言われた内容」と「日時」さえあれば、「あ、あそこで〇〇さんと居た時だ」と自分で逆引きできます。

**3つとも同じ流れです。** 聞いた日時 → その時どこに居たか → 相手は誰か。回すのが周りの人か、本人かが違うだけ。
今はこの手がかり（見出し・タグ）が全部落ちてしまうので、詰みます。「どこで誰に何を言われたか」が丸ごと分からない。聞いた日時は、機械が確実に付けられるただ一つのタグで、そこから残りを人が引き戻します（4章の方針7）。

## 2. 動かし方

1. `kiiteru_nyan_v2.html` を Edge か Chrome で開く。（Vivaldi など他のブラウザは、画面は動いてもマイクでの聞き取りが動きません）
2. 「アプリを開く」→「✍ 文字で入れる」→「サンプル会話を入れてみる」→「ここから拾う」。まずこれで一通り動きます（マイク不要）。
3. マイクで試すなら「👂 聞いててにゃ」。マイクの許可を求められます。

**マイクを使う時の開き方**：ブラウザは、https か localhost で開いたページにしかマイクを渡しません。Edge では、ファイルをダブルクリックで開いた状態（アドレスが `file:///…`）のままで動きました。通らない時は、ファイルのあるフォルダで `python -m http.server 8000` を実行し、Chromeで `http://localhost:8000/kiiteru_nyan_v2.html` を開いてください。開き方が変わると保存場所も別になるので、前に入れた一覧は出ません。

**スマホで試す時**：このファイルを https で配れる場所（GitHub Pages など）に置く必要があります。PCで立てたサーバーにスマホから繋ぐ方法では、マイクが許可されません。

## 3. いま動くこと／まだ動かないこと

**動く**

- 聞く：ボタンを押している間、ブラウザの音声認識で文字にする
- 文字で入れる：会話を貼って試せる（マイクなしの確認用）
- 拾う：文字から予定／手順を抜く。「かんたん版」（正規表現・鍵いらず）と「LLM版」（設定で切替）
- 見せる：予定／手順のタブ、近い順の並び、「つぎはこれにゃ」
- 選ぶ：カレンダーに入れる（日時を本人が確かめてから `.ics` を書き出し）／大事マーク／捨てる（すぐなら戻せる）／予定⇔手順の移し替え
- しぼる：「いつ頃 聞いた話か」で絞る。言葉で探す（奥に置いた補助）
- 開くたび「つぎは〇〇」がそっと出る（アプリ内）
- 保存：ブラウザ内に保存。JSONで書き出せる

**まだ動かない（＝お願いしたい所。7章）**

- 常時聞き取り（画面を閉じても聞く）。ブラウザでは画面を閉じるとマイクが止まるため、v2 は「開いて押している間だけ」
- 本物のロック画面・通知への表示
- カレンダーへの直接登録（今はファイル書き出し）

## 4. 変えないでほしい方針

改良の時、ここだけは錨にしてください。善意の改良で一番壊れやすい所です。

1. **杖であって、代行ではない。**
   決めるのは本人です。アプリが勝手にカレンダーに入れる、勝手に予定を確定する、はやりません。拾うまでがアプリの仕事、選ぶのは本人の仕事。日時も「っぽい」だけなので、入れる前に必ず本人に確かめてもらいます。
   判断の物差し：その機能は **本人の行きたい所** に仕えているか、それともアプリの行きたい所か。

2. **先に出す（push）。探させない（pull しない）。**
   相手は「検索できない」人です。何を探せばいいかを思い出せないから困っている。だから開いたらもう一覧が出ている、が基本形。検索は奥に置いた補助で、出番がないのが正常です。

3. **「らしきもの」で止める。**
   完璧な書き起こしは目指しません。「〜っぽい」で拾い、`?` を付けて出します。断定する表示にすると、間違っていた時に本人がそれを信じて動いてしまいます。拾いもらしより拾いすぎの方がまし（捨てればいいので）。

4. **思い出させない。見て選ばせる。**
   入力欄に書かせる、分類させる、設定させる、は極力なし。出ているものを見て、要る／違うを押すだけ。元の言葉も一緒に見せます（見れば「あ、あれか」と分かるため）。

5. **非難しない。**
   「忘れています」「未対応3件」のような責める文言、赤いバッジ、催促はやりません。ネコの口調と「ちょっとテキトーに拾ってきた感」は飾りではなく、間違いを許せる空気を作るための機能です。

6. **一点から。**
   機能を足す前に、この一本（聞く→拾う→選ぶ）の質を上げる方を優先してください。

7. **分からなかったら、誰かに見せる。それが逃げ道。**
   「選べない」の手前に、「代わりに選んでほしいことを、自分では言葉に出せない」があります。このリストは、差し出せばそのまま質問になる紙です。「わかんなかったら、誰かにこのリスト見せてね」で、間違って拾ったものも、あいまいな日時も、かなり片付きます。
   支援する側も「何があったか分からない、本人に訊いてもやっぱり分からない」で困っています。本人の気持ちまではすぐ分からなくても、「何がどうした」が見えるだけで埋められる部分は大きい。
   ここから出てくる作り方：
   - `?` は消さない。弱点の表示ではなく、訊くきっかけです。自動で確定させると、本人が訊く機会も、周りが間違いに気付く機会も一緒に消えます。
   - 当てる精度より、**拾いもらさないこと**と、**初めて見る人が一目で分かること**（元の言葉、いつ聞いたか、できれば誰が言ったか）を優先。
   - 基本の形は「本人が見せる」。
   - **聞いた時刻は、機械が保証できる数少ない事実**です。日時が分かれば居場所が分かり、居場所が分かれば相手が絞れます。聞いた瞬間の時刻を打ち、推測で埋めたり後から書き換えたりしない（抜き出しを後でまとめて行う作りにしても、時刻は聞いた時のもの）。
   - 突き合わせて篩にかけるのは人の仕事で、アプリは「合っている／おかしい」を判定しません。また「リストに無い」は「言われていない」の証拠にはなりません（聞き逃し・電源・雑音がある）。

8. **「誰かが居ないと回らない」を作らない。**
   福祉は、作った人が居なくなっても続きます。だから「この人が抜けたら回らない」は、会社よりずっとまずい。学校の先生が一人抜けたら学校が崩れる、では子どもも親も地域も困るのと同じです。楽をしたいからではなく、この分野では絶対に避けないといけないことです。
   開発者として名を上げるのは一向に構いません。でも「この人が居ないと動かない」物にはしないでください。困るのは、たくさんの弱い立場の人です。目指すのは紙オムツです。誰が発明して誰が広めたのか誰も知らないけれど、みんなが使っている。
   「誰か」には、人だけでなく、会社や特定のサービスも入ります。
   - 分かったこと・決めたことは文書に残す（この文書もそのためです）。
   - 部品は差し替えられる形を保つ（5章）。
   - 特定の会社のサービスが止まったら使えなくなる、という作りにしない（7章の9）。

## 5. 構成と差し替え口

1ファイルの中が2つのスクリプトに分かれています。

- `<script id="core">`：画面に触らない純粋なロジック（日付の解決、かんたん版の抜き出し、LLM用プロンプト、.ics 生成）。Node でそのまま読めるのでテストしやすい。
- `<script id="app">`：部品と画面。

差し替えを想定している部品は2つです。

| 部品 | 役目 | 約束（インターフェース） | いまの中身 |
|---|---|---|---|
| `Listeners` | 聞く→文字 | `supported()` / `start({onInterim, onFinal, onState, onError})` / `stop()` | ブラウザ内蔵の音声認識（Web Speech API、`ja-JP`） |
| `Extractors` | 文字→らしきもの | `async (text, now) => [item…]` | `rule`（正規表現）／`llm`（OpenAI互換 または Anthropic） |

保存（`Store`）は localStorage。`all / get / add / update / clear` の5つを保てば差し替えられます。
ブラウザのコンソールから `Kiiteru.feed('明日の14時に歯医者', 'text')` のように直接流し込めます。

**1件のデータの形**

```
id, kind('yotei'|'tejun'), title, quote(もとの発話),
date(YYYY-MM-DD|null), time(HH:MM|null), timeLabel('午後'など|null),
approx('来週'など|null), anchor(並べ替え用の目安日|null), whenText,
heardAt(聞いた時刻), status('new'|'calendar'|'discarded'),
starred, confirmed(本人が日時を確かめたか), source('mic'|'text'), extractor('rule'|'llm')
```

捨てたものも `discarded` として残してあります（一覧には出ません）。書き出したJSONは「本人が違うと言った拾い方」の記録になるので、抜き出しの改良・評価に使えます。

## 6. どこに何が出ていくか

- 拾った一覧：その端末のブラウザの中だけ。**録音は残しません**。文字も、拾った項目とその元の一言だけを保存します（会話全体は残しません）。
- かんたん版：文字を外に出しません。
- LLM版：会話の文字を、設定した宛先に送ります。APIキーはブラウザに保存されます（試作用の割り切り）。
- 文字起こし：ブラウザの音声認識は、既定では音声を外部のサーバーに送って処理します。端末内で処理する指定（`processLocally`）も新しいChromeにはありますが、日本語で使えるかは未確認です。
  参考：[MDN: Using the Web Speech API](https://developer.mozilla.org/docs/Web/API/Web_Speech_API/Using_the_Web_Speech_API) ／ [MDN: processLocally](https://developer.mozilla.org/docs/Web/API/SpeechRecognition/processLocally)

周りの人の声も入るアプリなので、ここは技術だけでなく運用の設計が要ります（7章の8）。

## 7. お願いしたい所

弱い順ではなく、効きそうな順です。

1. **抜き出しの質**：かんたん版は正規表現の当て推量。LLM版のプロンプト（core の `buildLLMPrompt`）も叩き台です。評価用の会話セットを作る所から。
2. **文字起こしの質**：雑音、複数人、離れた声、方言。
   「誰が言ったか」（話者の区別）は、機械で当てなくても辿れることが多いです。日時が分かれば「その時どこに居たか」が分かり、「あそこに居たのは〇さん」「とりあえずその場所に訊いてみよう」と進められます。今は本人も支援者もそこまで辿り着けていません。なので話者の区別より先に、**いつ聞いたか（日付・曜日・時刻）を正確に残して、見せる**方が効きます（方針7）。
3. **常時聞き取り**：画面を閉じても聞ける形（専用アプリ／専用端末）。電池と発熱。
4. **ロック画面・通知での「つぎは〇〇」**：開くたびそっと出て、すぐ消える。鳴らし方も含めて、責めない出し方で。
5. **予定の更新と重複**：「やっぱり15時に変更」「同じ話を3回聞いた」の扱い。今は同じ文言を二度拾わないだけです。
6. **文をまたぐ話のつながり**：かんたん版は一文ずつバラバラに見ています。実例：「明日は泊りで病院行く日だよ。9時に出発だからね」と入れると、2件に分かれ、2件目（9時に出発）は「明日」を引き継げず日付が「いつ?」になります。本人にとっては「明日・病院・9時出発」で一つの用事です。拾う単位を"文"から"用事"にする、が5と共通の根っこです。
7. **カレンダー直接連携**：今は `.ics` 書き出し。
8. **同意とプライバシーの設計**：周りの人の声が入ること、福祉の現場で使う時のルール、どこまで保存するかの線引き。
9. **外に出さない構成**：端末内の文字起こし＋ローカルLLMで完結できるか。これは最終目標で、後回しで構いません。ただ、途中の作りが大きなクラウドのLLM頼みになると後で載せ替えられなくなるので、節目ごとに小さいモデルでも試しておいてください。
10. **手順の見せ方**：今は一覧に置くだけ。必要な場面で出す方法（ただし方針1・5の範囲で）。
11. **見せる場面の作り**：本人が誰かに差し出して見せる時の画面（大きく、元の言葉つきで、初めて見る人にも分かる形。方針7）。支援者が本人を通さずに見る形が要るか、要るならどこまでか、はまだ決めていません。

## 8. 既知の弱点・確かめられていないこと

- **確認済み**：抜き出しロジックのテスト（24例）、画面の一通りの操作（拾う・カレンダー書き出し・捨てる/戻す・しぼる・さがす・設定・再読み込み後の保持）をChromeで自動実行して通過。
- **マイク（実機）**：Windows の Edge と Chrome で、ファイルを直接開いた状態で聞き取りから一覧まで動作（20261117）。Vivaldi では動かず。聞き取りの中身はブラウザごとに別物です（下の「お迎え」は Edge では「お願い」になり、Chrome では正しく取れた。ただし各1回ずつ）。
- **未確認**：実際のLLMサービスへの接続。APIキーが無かったため、模擬のサーバーで配線だけ確かめています。ブラウザから直接呼べるかはサービス側の設定次第なので、通らない時は小さな中継サーバーを挟んでください。
- **聞き間違いは、そのまま載ります。** 実例：「お迎えに行く」が「お願いに行く」と聞き取られ、日時は合っていた。一覧に出る言葉は「言われた言葉」ではなく「機械が聞き取った言葉」で、これも"っぽい"の一部です。録音を残さない作りなので、後から聞き直して確かめる手段はありません（短い音だけ残すかどうかは、7章の8と合わせて要検討）。
- 聞いた時刻の表示は、2日以上前になると「3日前」のように日数だけになり、曜日と時刻が落ちます（データには残っています）。方針7の使い方には足りません。
- かんたん版は一文ずつ見るので、前の文の「明日」を次の文に引き継ぎません（7章の6の実例）。
- かんたん版は、時刻や曜日が出てくる雑談も拾います（「8時に起きた」など）。「3時」は午後と当て推量します。タイトルは話した言葉そのままです。
- 音声認識の結果に句読点が入るかはブラウザ次第です（Edge は入る）。入らない場合、長く話し続けると1件が長くなります。
- 月をまたぐ「25日」や年をまたぐ日付は単純な規則で解決しています。
- スマホは未確認です。https の置き場所が要るほか、今の「聞きっぱなし」の設定（`continuous`）は iPhone の Safari で不安定という報告が多く、手直しが要る見込みです。

## 9. この先（見えている範囲）

今は作りません（方針6）。ただ、この先に何を置いているかを知っておいてもらうと、今の作りを決める時の助けになります。

土台は一冊の帳面です。「いつ・何を聞いたか」を時刻つきで貯めたもの。聞いてるニャはその最初の見せ方で、以下は同じ帳面の別の見せ方です。近い順に並べています。

- **日報**：本人が言えない代わりに、その日の「何がどうした」を、連絡ノートや医師・支援者に渡せる形にする。現場では各所の連絡ノートへの記入が命綱です。誰にどう届けるか（本人が渡すのか、直接届くのか）は未定（7章の11）。
- **指示の復唱**：医師・看護師・支援員の指示を書き留め、易しく言い換える。聞き間違いが怖い場面なので、聞き取った言葉と言い換えを並べて出し、その場で言った相手に見せて確かめてもらう。
- **誘導（歯磨き・薬など）**：支援員の手が足りず抜けることがある所を補う。機械の方から声をかける最初の機能なので、責めない言い方が要る。薬だけは、会話から拾った"っぽい"情報では動かさず、支援者が確定して入れた内容だけで動かす。
- **持ち歩ける専用機**：外に繋がらず、ポシェットに入れて持ち歩ける形（7章の9）。
- **遠い先**：目で見て案内する（盲導犬のような誘導、買い物中に「それ冷蔵庫にあるよ」）。帳面に書き込む入口が、耳から目に増える形です。
